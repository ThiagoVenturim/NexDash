# Comparison with similar tools

nexdash is a small Python engine that answers questions and builds dashboards through a
semantic layer, and serves them over MCP and REST to other programs. Several projects
cover parts of the same ground. This page says where nexdash differs and what it lacks.
It is based on the survey in [REFERENCIAS.md](REFERENCIAS.md) (Portuguese, November
2026); features of other projects change, so check each one before relying on this
table.

## Overview

| Project | Kind | Natural language | Semantic model | How queries reach the database |
| --- | --- | --- | --- | --- |
| nexdash | Embeddable engine (Python, MCP, REST) | Yes, through a `nexcoder-core` model tier | YAML cubes | Plan compiled through an allowlist into parameterized SQL |
| Wren AI | Text-to-SQL and text-to-chart application | Yes | MDL (modeling definition language) | Model writes SQL constrained by the MDL |
| Cube | Universal semantic layer between sources and BI tools | Not covered by the survey | Cube data models | Generated by Cube from its query API |
| Lightdash | BI on top of dbt projects (governed, versioned) | Not covered by the survey | dbt models and metrics | Generated from dbt metadata |
| Metabase, Superset | Classic open-source BI | Not covered by the survey | No strong native semantic layer | Query builders and free SQL editors |
| ThoughtSpot, Power BI Copilot, Tableau, Looker | Commercial BI | Yes | Proprietary (for example LookML in Looker) | Vendor-specific |

Smaller projects in the same space include Drizby / drizzle-cube (BI over a TypeScript
semantic layer), Synmetrix, OrionBelt and OpenChatBI.

## Where nexdash differs

- **The model never writes SQL.** Wren AI is the closest project and also restricts the
  model with a semantic model, but its output is still SQL. nexdash takes a typed JSON
  plan and writes the SQL itself, so a bad answer fails validation instead of running.
  See [SQL_GUARDS.md](SQL_GUARDS.md).
- **Built to be called by programs.** nexdash has no workspace, user management or
  dashboard editor. Other projects call it over MCP or REST with scoped tokens (see
  [REPORT_ENGINE.md](REPORT_ENGINE.md)), and agents publish their own HTML pages as
  [live dashboards](LIVE_DASHBOARDS.md) with the data injected by the server.
- **Open or paid models.** The model tier maps to Ollama, vLLM or a paid API through
  `nexcoder-core` configuration, with no vendor-specific code in nexdash.
- **Work-tracking data built in.** Connectors for GitHub, Azure DevOps, Redmine, Jira and
  generic REST APIs feed a `work_items` cube and the ready-made report models
  (development productivity, security posture, support metrics). See
  [CONNECTORS.md](CONNECTORS.md) and [REPORT_MODELS.md](REPORT_MODELS.md).

## What nexdash lacks today

- **Expressive modeling.** Cubes have dimensions, simple aggregations, declared joins and
  filter allowlists. There are no derived metrics, row-level access rules, or column
  allowlists on joined tables. Wren AI's MDL, Cube and LookML go further.
- **Ecosystem compatibility.** Cubes are not dbt models and do not follow an existing
  semantic layer specification.
- **Chart selection.** A plan returns rows; choosing the chart is left to the dashboard
  author. Wren AI suggests charts from the question.
- **Exploration UI.** The web UI is minimal. Metabase and Superset offer full query
  builders.
- **Persistence of live dashboards.** `DashboardStore` keeps dashboards in memory; the
  host application has to persist them.
